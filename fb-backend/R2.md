# Temporary Cloudflare R2 storage

Set these backend-only environment variables on the single FileForge server:

```text
FILE_STORAGE_MODE=r2
R2_ACCOUNT_ID=<Cloudflare account ID>
R2_BUCKET=<private bucket name>
R2_ACCESS_KEY_ID=<R2 S3 API access key>
R2_SECRET_ACCESS_KEY=<R2 S3 API secret>
R2_REF_SIGNING_SECRET=<independent random secret, at least 32 bytes>
```

Optional settings: `R2_UPLOAD_URL_SECONDS` and `R2_DOWNLOAD_URL_SECONDS` default to 300 seconds. `FILE_CLEANUP_TTL_MINUTES` defaults to 30 minutes and controls local and R2 retention. With `FILE_STORAGE_MODE=local` (the default), the existing multipart/local-disk processing routes remain available. In R2 mode, processing routes take JSON object references; the legacy permanent `/files/upload` route is separate.

Create a private R2 bucket and a bucket-scoped **Object Read & Write** S3 API token. Configure bucket CORS for the browser origin, with `PUT` and `GET` methods and `Content-Type` in allowed headers. Keep the access key, secret, and reference-signing secret on the backend only. An R2 lifecycle rule for `temp/` is useful as a coarse backup if the server is down; the backend performs the 30-minute cleanup on startup and periodically while running.

Request flow:

1. For each source file, `POST /files/r2/upload-url` with JSON `{ "name": "report.pdf", "size": 12345, "type": "application/pdf" }`. The response contains a short-lived `url`, `method`, `headers`, and a signed `object` reference. The server chooses the `temp/input/` key.
2. The browser sends the raw file bytes directly to `url` using `PUT` and the exact returned `Content-Type` header.
3. Call the normal tool endpoint with JSON. Single-file tools receive `{ "file": <object>, ...toolOptions }`; merge, batch, and ZIP receive `{ "files": [<object>, ...], ...toolOptions }`. Array order is the processing order. The backend checks count, declared sizes, and types before queueing, then downloads each object under the job slot and rechecks actual size, MIME, file signature, and applicable page limits before conversion.
4. A successful response keeps the tool's existing metadata and adds `output` (a signed `temp/output/` reference) and `downloadUrl` (a short-lived presigned GET URL). The browser downloads directly from R2. `POST /files/r2/download-url` with `{ "object": <output> }` refreshes the GET URL while the output reference remains valid.

The backend deletes processed input objects and local staging files after success or failure. Output objects expire under the configured TTL. Signed PUT URLs restrict the key and content type, but R2 does not enforce the declared byte length at URL issuance; the backend checks actual length before processing. An unused or oversized direct upload may remain in R2 until the cleanup sweep. This backend has no browser UI yet, so a future frontend must perform the above API calls.
